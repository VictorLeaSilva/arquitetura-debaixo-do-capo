## Base e spec antes do código
- **Base:** `main` em `6246652` (merge do PR #12, `docs/spec-T-007`).
- **Lacuna surgida na execução, Q-027:** a conferência dentro da imagem `cassandra:5.0.9-trixie` mostrou que o Cassandra 5 usa o coletor G1 (`-XX:+UseG1GC` em `/etc/cassandra/jvm17-server.options`) e que o `cassandra-env.sh` manda definir só o `MAX_HEAP_SIZE` com o G1; o `HEAP_NEWSIZE` pedido pelo contrato seria ignorado, com o aviso "HEAP_NEWSIZE has erroneously been set and will be ignored in combination with G1". O compose define só o `MAX_HEAP_SIZE`, e o contrato foi corrigido. O autor pediu para seguir sem a pergunta; a recomendação foi aplicada e fica para ele confirmar na aprovação.

## Confirmação dentro das imagens (antes da primeira medição)
- **Cassandra:** o `cassandra-env.sh` só calcula o *heap* sozinho quando `MAX_HEAP_SIZE` está vazio ("Only use the calculated size if it's not set manually"). Em todas as rodadas, o processo `java` de cada nó rodou com o `-Xmx` pedido (`-Xmx512M` ou `-Xmx1G`, nos 3 nós). O `cqlsh` existe na imagem em `/opt/cassandra/bin/cqlsh`, mas fora do `PATH`; o script usa o caminho completo.
- **MongoDB:** `db.serverStatus().wiredTiger.cache["maximum bytes configured"]` = `268435456` (0,25 GiB) nos 3 membros, em todas as rodadas: o `--wiredTigerCacheSizeGB 0.25` vale.

## Teste primeiro
Um spike não tem teste automatizado: os critérios são provados por medições (G4). A primeira execução do roteiro serviu de teste dele próprio:
1. **Primeira tentativa, `cassandra 512M`:** o cluster subiu, mas a carga falhou em silêncio (10 s para 10.000 inserções) e o roteiro parou com `FALHA: Cassandra contou '', esperado 10000`, limpando tudo. **Causa:** no Git Bash, o MSYS traduz argumentos que começam com `/` em caminhos do Windows; `/opt/cassandra/bin/cqlsh` chegava ao `docker` como `C:/Program Files/Git/opt/cassandra/bin/cqlsh` (reproduzido com um nó só: `exec: "C:/Program Files/Git/opt/cassandra/bin/cqlsh": ... no such file or directory`; pelo `sh -c` dentro do container, o mesmo `cqlsh` respondia `5.0.9`).
2. **Correções no roteiro:** `export MSYS_NO_PATHCONV=1` (no Linux não faz nada); os caminhos do próprio script passaram a ser resolvidos no formato do Windows (`pwd -W`, com o `pwd` normal no Linux), porque, sem a tradução, o `docker compose -f /c/dev/...` deixaria de funcionar; os erros da carga passaram a ir para um arquivo e aparecem na mensagem de `FALHA`.
3. **Segunda tentativa:** completa, com o resultado do AC-T007.1.

## O que os números mostram
- Cada nó do Cassandra usou de 1.076 a 1.241 MiB com um *heap* de 512 MB: a memória de uma JVM é o *heap* mais o que fica fora dele (metaspace, threads, buffers e caches nativos).
- Com 1 GB de *heap*, o pico chega a 91% do limite: cabe, mas sem folga. A proposta para a fatia 6 (registrada na H-05) é usar 512 MB por nó.
- A variação entre as repetições do MongoDB (1.629,5 contra cerca de 1.050 MiB) veio do container de observabilidade, que oscilou de 563 a 1.060 MiB; os nós do MongoDB ficaram entre 120 e 304 MiB.

## Armadilha nova do ambiente (follow-up para o `05 §9`)
- **Tradução de caminhos do MSYS no Git Bash:** um argumento que começa com `/` (por exemplo, um caminho dentro de um container) é convertido em caminho do Windows antes de chegar ao `docker`. Use `MSYS_NO_PATHCONV=1` e passe os caminhos do host no formato do Windows (`pwd -W`).

## Armadilha nova (follow-up para o `05 §9`)
