**Função `sdd_deps_custom <rev>` (no próprio `sdd.conf`, Q-016).** Lê os arquivos com `git show "$rev:<arquivo>"` e imprime uma coordenada por linha (o script já ordena e tira as repetidas):
1. Para cada `pom.xml` da revisão (`git ls-tree -r --name-only "$rev"`):
   - o bloco `<parent>`: `groupId:artifactId:version`;
   - cada bloco `<dependency>` e cada bloco `<plugin>`: `groupId:artifactId:version` quando o bloco declara `<version>`; `groupId:artifactId` quando não declara (a versão vem do BOM). Um `<plugin>` sem `<groupId>` usa `org.apache.maven.plugins`, que é o padrão do Maven;
   - o `<groupId>`, o `<artifactId>` e a `<version>` dentro de `<exclusions>`, de `<configuration>` e de um `<dependencies>` aninhado num plugin **não** se misturam com os do bloco que os contém: o bloco aninhado é tratado como um bloco próprio (`<dependency>`), e o de `<exclusion>` é ignorado.
2. Para cada `.github/workflows/*.yml`: cada linha `uses: <dono>/<repo>@<ref>` vira `<dono>/<repo>@<tag>`, com a tag lida do comentário `# <tag>` na mesma linha; sem comentário, `<dono>/<repo>@<ref>`.
3. Nenhum outro arquivo (o `package.json` entra na T-016).

**`scripts/test/test-sdd-conf.sh`.** Testes próprios do `sdd.conf`, no estilo do `run-tests.sh` (um repositório git temporário por cenário, `PASSOU`/`FALHOU`, exit 1 se algum falhar). Cada cenário tem a linha `# covers: RNF-012`:
1. `pom.xml` com parent, uma dependência com versão, uma sem versão, um plugin com versão, um plugin sem `groupId` e uma dependência com `<exclusions>` → a saída de `deps_em HEAD` é exatamente a lista esperada (as coordenadas excluídas **não** aparecem).
2. Um plugin com `<dependencies>` aninhado → aparecem o plugin e a dependência aninhada, cada um com as próprias coordenadas.
3. Um workflow com `uses:` fixado por SHA com comentário e outro sem comentário → `actions/checkout@v7.0.1` e `dono/repo@<ref>`.
4. Num repositório com uma tarefa que permite só uma dependência, acrescentar um plugin novo no `pom.xml` → `verify-task.sh` reprova no item 3, citando a coordenada do plugin (AC-RNF-012.3).
5. Acrescentar um arquivo fora de `allowed_paths` → reprova no item 2; um teste Java novo sem `@Tag` do requisito coberto → reprova no item 4 (AC-RNF-012.2).
6. Uma linha `# covers: RNF-012` num arquivo de `scripts/test/` é reconhecida como marcação pelo `check-traceability.sh`.
- O teste carrega o `scripts/sdd.conf` **real** do projeto (copiado para o repositório temporário), para provar a configuração de verdade, e não uma cópia simplificada.

**CI.** Acrescentar ao `.github/workflows/ci.yml` o job `harness` (`ubuntu-latest`): checkout (mesma action e mesmo SHA já usados); `bash scripts/test/run-tests.sh`; `bash scripts/test/test-sdd-conf.sh`; `bash scripts/check-traceability.sh --check-file`. **Não** roda `check-traceability.sh` sem argumento: a lista "obrigatório sem teste" só fica vazia no fim do MVP (G5), e reprovaria todo PR até lá. Nenhuma action nova.

**Matriz.** Regenerar `docs/specs/traceability.md` com o `sdd.conf` novo (ela passa a marcar como "sim" os obrigatórios de `02 §3`).

**Segurança.** Os scripts não fazem rede e não leem segredos.

## Critérios de aceite
- **AC-RNF-012.1** Dado o repositório, quando `bash scripts/test/run-tests.sh` e `bash scripts/test/test-sdd-conf.sh` rodam no Git Bash e no job `harness` do CI, então todos os cenários passam e os dois scripts saem com `0`.
- **AC-RNF-012.2** Dados os cenários 5 de `test-sdd-conf.sh`, quando o gate roda, então reprova no item 2 com o arquivo fora do escopo e no item 4 com o requisito sem marcação.
- **AC-RNF-012.3** Dados os cenários 1 a 4 de `test-sdd-conf.sh`, quando `deps_em` e o gate rodam, então as coordenadas saem no formato de Q-016 e um plugin novo fora do contrato reprova o item 3.
- **AC-RNF-012.4** Dada uma linha alterada à mão em `docs/specs/traceability.md`, quando `bash scripts/check-traceability.sh --check-file` roda, então sai com `1` e a mensagem "desatualizado"; com a matriz regenerada, sai com `0`.
- **AC-T003.1** Dados os 7 scripts copiados, quando o SHA-256 de cada um é comparado com o da tabela de "Decisões", então todos são iguais.
- **AC-T003.2** Dado o commit da tarefa, quando `git ls-files -s scripts` roda, então todo `.sh` tem modo `100755`.
- **AC-T003.3** Dada esta tarefa, quando `BASE=main bash scripts/verify-task.sh T-003` roda a partir do repositório (e não da skill), então o item 1 executa o `cd backend && ./mvnw -q -B -ntp verify` de verdade (o log mostra o comando e o resultado verde), e o resultado geral é VERDE.
- **AC-T003.4** Dado um branch descartável num clone temporário, com um arquivo fora do escopo e um teste sem `@Tag` numa tarefa de exemplo, quando o gate do repositório roda, então reprova com as mensagens dos itens 2 e 4 (a violação proposital pedida pela skill).
