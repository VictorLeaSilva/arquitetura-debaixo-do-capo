## Objetivo
Deixar o repositório público protegido (a `main` só muda por PR com o CI verde, segredos barrados no push, dependências e código vigiados) e apresentável para quem chega pelo link de um post: uma página inicial que explica o projeto, arquivos de comunidade e uma imagem de prévia própria (RNF-013). A parte que só o autor pode fazer, nas configurações do GitHub, vira um roteiro explicado e conferido.

- `00-constitution`: P10, §4 (git do autor), DP-05 (padrão de explicação), DP-22 (palco × bastidores: nada pessoal nos arquivos públicos além do contato da Q-026).

- Tarefas anteriores: T-002 (CI e actions fixadas por SHA), T-004 (`compose.yaml`).

## Decisões da tarefa
**Pré-condição: o contato (Q-026).** Antes de escrever o código de conduta e o `SECURITY.md`, o autor informa o e-mail dedicado ao projeto. Sem ele, **parar**: nenhum e-mail pessoal entra no repositório.

**`CODE_OF_CONDUCT.md`.** O texto oficial do Contributor Covenant 2.1 em português do Brasil (`https://www.contributor-covenant.org/pt-br/version/2/1/code_of_conduct/`), sem alterações além de preencher o contato pelo e-mail da Q-026, com o link da origem e a versão no topo.

**`SECURITY.md`.** Seções: "Versões cobertas" (só a `main`, o projeto não publica releases); "Como relatar uma vulnerabilidade" (o caminho principal é o relato privado do GitHub, com o link `https://github.com/VictorLeaSilva/arquitetura-debaixo-do-capo/security/advisories/new`; a alternativa é o e-mail da Q-026); "O que esperar" (confirmação de recebimento em até 7 dias [meta] e o andamento combinado pelo próprio relato); "Escopo" (é um laboratório local, sem ambiente de produção; um relato sobre os experimentos "ruins" de propósito não é vulnerabilidade, explicando por quê); "Por favor, não abra uma issue pública para vulnerabilidades".

**`CONTRIBUTING.md`.** Em português, no padrão DP-05: como o projeto é construído (SDD, com link para `docs/specs/00-constitution.md` e `AGENTS.md`); como propor uma mudança (abrir uma issue primeiro); branches e commits (`task/T-xxx-slug`, Conventional Commits); o que o PR precisa passar (`cd backend && ./mvnw -q verify`, os testes do harness e o CI); idioma (código em inglês, documentação em português); licenças das contribuições: quem contribui licencia o código sob a MIT e a documentação sob a CC BY-NC-SA 4.0, as mesmas do repositório.

**`.github/CODEOWNERS`.** Uma linha: `* @VictorLeaSilva`.

**`.github/PULL_REQUEST_TEMPLATE.md`.** Campos: tarefa (`T-xxx`) ou motivo; o que muda; critérios de aceite cobertos; e um checklist: gate verde (`scripts/verify-task.sh`); evidência registrada; README atualizado e comandos executados em bash e PowerShell (ou N/A); revisão independente PASS; checklist de pronto da tarefa marcado.

**`.github/ISSUE_TEMPLATE/`.** Formulários do GitHub (YAML): `bug.yml` (o que aconteceu, o que era esperado, passos, ambiente: sistema, shell, versão do Docker e do JDK); `sugestao-de-experimento.yml` (o conceito, a pergunta que o experimento responde, as versões ruim e boa imaginadas, o que seria medido); `config.yml` com `blank_issues_enabled: false` e um link de contato para o relato privado de vulnerabilidade.

**`.github/dependabot.yml`** (`version: 2`), com três entradas, todas com `schedule.interval: weekly` (segunda-feira), `open-pull-requests-limit: 5`, mensagem de commit com o prefixo `build(deps)` e um grupo que junta as atualizações *minor* e *patch* num PR só (as *major* vêm separadas):
| `package-ecosystem` | `directory` | O que atualiza |
|---|---|---|
| `maven` | `/backend` | parent, dependências e plugins do `pom.xml` |
| `github-actions` | `/` | as actions dos workflows |
| `docker-compose` | `/` | as imagens do `compose.yaml` |

Cada PR do Dependabot é tratado como uma tarefa: muda `docs/versoes.md` e é revisado como qualquer outro (fica registrado no `CONTRIBUTING.md`).

**README de apresentação.** O topo do `README.md` ganha, antes das seções que já existem (que continuam iguais): título; uma frase do que é; badges do CI e das duas licenças; "O que é" (o laboratório e a ideia de comparar versões ruim, média e boa, medidas); "O que você vai encontrar" (os 3 experimentos do MVP, numa frase cada, marcados como "em construção"); "Roteiro" (as 10 fatias, de `docs/produto/visao.md`); "Como o projeto é construído" (SDD, specs, revisão independente, com links); e, no fim, "Como contribuir", "Segurança" e "Código de conduta", com links para os três arquivos. Nenhuma promessa de resultado que ainda não foi medido (P7).

**Imagem de prévia (Q-024).**
- `docs/assets/social-preview.svg`: 1280 × 640, fundo escuro, o nome "Arquitetura Debaixo do Capô", a frase "Conceitos de arquitetura de software, medidos lado a lado" e três marcas visuais ruim / médio / bom (sem logotipos de terceiros, só texto e formas).
- `scripts/gerar-preview-social.sh`: gera `docs/assets/social-preview.png` a partir do SVG com o Chromium sem tela da imagem Docker `chromedp/headless-shell`, numa tag **numérica fixa** (a estável mais recente no Docker Hub na data da execução, registrada em `docs/versoes.md`), com `--window-size=1280,640` e `--screenshot`. O PNG final precisa ter 1280 × 640 e menos de 1 MB.

**`docs/repositorio/configuracoes-github.md`: o roteiro do autor.** Para cada configuração: o que é, o que protege, onde fica (o caminho no menu do GitHub, em português e com o nome em inglês que aparece na tela), o valor e como conferir. As configurações:
1. **Ruleset da `main`** (Settings → Rules → Rulesets): "Restrict deletions", "Block force pushes", "Require a pull request before merging" (0 aprovações: o autor trabalha sozinho e o GitHub não deixa aprovar o próprio PR), "Require status checks to pass before merging" com `build`, `harness` e `secrets` (o `dependency-review` só roda em PR e entra também), "Require branches to be up to date before merging"; **sem** ninguém na lista de exceção (*bypass*), para valer também para o dono.
2. **Merge** (Settings → General → Pull Requests): só "Allow squash merging", com o título do PR como mensagem; "Automatically delete head branches" ligado (Q-025).
3. **Segurança** (Settings → Security and quality → Advanced Security): Dependency graph (já ligado na T-002), Dependabot alerts e Dependabot security updates, Secret Protection com "Push protection", Code scanning com o CodeQL na configuração padrão (*default setup*; o Java é analisado sem compilar), "Private vulnerability reporting".
4. **Actions** (Settings → Actions → General): "Require actions to be pinned to a full-length commit SHA"; permitir só as actions da GitHub e as listadas (`gitleaks/gitleaks-action`); "Workflow permissions" só de leitura; "Allow GitHub Actions to create and approve pull requests" desligado.
5. **Conta:** autenticação em dois fatores ativa na conta do autor.
6. **Apresentação** (página do repositório → engrenagem ao lado de "About"): descrição, *topics* (`software-architecture`, `java`, `spring-boot`, `system-design`, `big-o`, `design-patterns`, `observability`, `docker`, `sdd`, `portuguese`) e, em Settings → General → Social preview, o upload do `social-preview.png`.
- O roteiro termina com uma tabela de conferência que o autor marca, e cada item diz se dá para conferir pela API pública do GitHub (comando `curl` em bash e PowerShell) ou só pela tela.

**Segurança.** Nenhum dado pessoal além do e-mail dedicado da Q-026 e do nome que já está na licença. Nenhuma credencial.

## Critérios de aceite
- **AC-RNF-013.1** Dado o ruleset ativo, quando a API pública `GET /repos/VictorLeaSilva/arquitetura-debaixo-do-capo/rules/branches/main` é consultada, então ela lista as regras de deleção, de *force push*, de PR obrigatório e de status obrigatórios (com `build`, `harness`, `secrets` e `dependency-review`); e um `git push origin HEAD:main` direto, feito pelo autor, é recusado pelo GitHub.
- **AC-RNF-013.2** Dado o repositório configurado, quando o autor tenta enviar, num branch descartável, um commit com uma chave de acesso falsa no formato reconhecido pelo GitHub, então o push é bloqueado ("push protection"), e nada chega ao GitHub; e a lista de execuções do Actions mostra uma análise do CodeQL concluída.
- **AC-RNF-013.3** Dada a página inicial do repositório, quando ela é aberta, então mostra o README de apresentação com as seções da decisão, e o GitHub lista `SECURITY.md`, `CONTRIBUTING.md` e `CODE_OF_CONDUCT.md` como arquivos de comunidade (`GET /repos/.../community/profile`, com `health_percentage` de 100 ou com os itens ausentes justificados na evidência).
- **AC-T008.1** Dado o `.github/dependabot.yml`, quando o GitHub o lê, então não há aviso de erro de configuração, e a primeira verificação do Dependabot roda para os três ecossistemas (Insights → Dependency graph → Dependabot), com o resultado registrado na evidência.
- **AC-T008.2** Dado o SVG, quando `bash scripts/gerar-preview-social.sh` roda no Git Bash, então gera `docs/assets/social-preview.png` com 1280 × 640 pixels e menos de 1 MB; e o mesmo comando, rodado de novo, gera um PNG idêntico ao anterior (SHA-256 igual).
- **AC-T008.3** Dadas as configurações de merge e do Actions, quando o autor confere as telas do roteiro, então só o *squash merge* está permitido, os branches são apagados depois do merge, as actions precisam de SHA completo e o token dos workflows é só de leitura; e uma action fixada por tag, num branch de teste, faz o workflow falhar.
- **AC-T008.4** Dada a seção "About", quando a API pública `GET /repos/VictorLeaSilva/arquitetura-debaixo-do-capo` é consultada, então `description` e `topics` têm os valores do roteiro; e o link do repositório, colado num post do LinkedIn (sem publicar), mostra a imagem de prévia.
- **AC-T008.5** Dado o `CODE_OF_CONDUCT.md`, quando comparado com o texto oficial da tradução 2.1 em português, então a única diferença é o contato preenchido e o cabeçalho com a origem.
