**Como obter o wrapper sem ter o Maven instalado.**
1. Gerar um projeto em `https://start.spring.io` com: Project **Maven**, Language **Java**, Spring Boot **4.1.2**, Group `io.github.victorleasilva`, Artifact `arquitetura-debaixo-do-capo`, Package name `io.github.victorleasilva.capo`, Packaging **Jar**, Java **25**, dependências **Spring Web** e **Spring Boot Actuator**.
2. Aproveitar do zip apenas `mvnw`, `mvnw.cmd` e `.mvn/wrapper/maven-wrapper.properties`, copiados para `backend/`.
3. Em `maven-wrapper.properties`, deixar exatamente: `wrapperVersion=3.3.4`, `distributionType=only-script` e `distributionUrl=https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.10.0/apache-maven-3.10.0-bin.zip`. Com `only-script`, nenhum `.jar` binário entra no repositório.
4. Se o zip gerado tiver, para "Spring Web", um artefato diferente de `spring-boot-starter-webmvc` (e, nos testes, de `spring-boot-starter-webmvc-test`), **parar e registrar uma Q**: os nomes de `allowed_new_dependencies` vêm da reorganização dos starters na linha 4.x e precisam bater com o que o Spring gera para a 4.1.2.

## Critérios de aceite
- **AC-T001.1** Dado um clone limpo do repositório numa máquina com JDK 25 e **sem** Maven instalado, quando `cd backend` e `./mvnw -q verify` são executados no bash, então o comando termina com código de saída `0`, e o wrapper baixa o Maven 3.10.0.
- **AC-T001.2** Dado o mesmo clone, quando `cd backend` e `.\mvnw.cmd -q verify` são executados no Windows PowerShell 5.1, então o comando termina com código de saída `0`.
- **AC-T001.3** Dada a aplicação, quando o teste `CapoApplicationTests` faz `GET /actuator/health`, então a resposta é `200` com `"status":"UP"`.
- **AC-T001.4** Dada a regra `requireJavaVersion`, quando ela é trocada temporariamente para `[99,)` e `./mvnw -q validate` é executado, então o build falha com uma mensagem do enforcer citando a versão do Java; e, ao desfazer a troca, o build volta a passar.
- **AC-T001.5** Dada uma dependência temporária com versão `LATEST`, e depois outra com versão `1.0-SNAPSHOT`, quando `./mvnw -q validate` é executado, então o build falha nas duas, citando `banDynamicVersions` e `requireReleaseDeps`; e, ao remover as dependências, volta a passar.
- **AC-T001.6** Dados `LICENSE` e `LICENSE-docs`, quando comparados, então `LICENSE` é o texto MIT com o copyright de 2026, e o texto de `LICENSE-docs`, sem a linha de cabeçalho, tem o mesmo SHA-256 do arquivo oficial `legalcode.txt` baixado no momento da verificação; o README cita as duas licenças e o que cada uma cobre.
- **AC-T001.7** Dado `docs/versoes.md`, quando comparado com `backend/pom.xml` e `maven-wrapper.properties`, então as versões de Spring Boot, Maven, Maven Wrapper e enforcer são idênticas, e cada linha tem link oficial e a data em que foi conferida.
- **AC-T001.8** (corrigido pela Q-014) Dados os arquivos novos, quando `git ls-files --eol` é executado depois do `git add`, então todos os arquivos de texto aparecem como `i/lf` (é assim que o git os guarda); `backend/mvnw.cmd` aparece com `attr/text eol=crlf` e, depois de um checkout, com `w/crlf` na pasta de trabalho; e `backend/mvnw` tem o bit de execução no índice do git (`git ls-files -s backend/mvnw` começa com `100755`).
- **AC-RNF-010.1** Dada a T-001 concluída, quando o checklist de pronto é marcado, então `.bastidores/registro-horas.md` tem a linha "Pré-T-001" e a linha da T-001, por tipo de trabalho.
