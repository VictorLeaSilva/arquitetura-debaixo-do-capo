## Decisões da tarefa
**Versões** (conferidas nas páginas oficiais em 2026-11-09; vão para `docs/versoes.md`):
| Item | Versão (tag da imagem) | Fonte |
|---|---|---|
| PostgreSQL | `postgres:18.6-trixie` | postgresql.org/support/versioning (18.6 é a versão GA mais recente; a 19 está em RC1) e hub.docker.com/_/postgres |
| Observabilidade | `grafana/otel-lgtm:0.40.0` | github.com/grafana/docker-otel-lgtm/releases ("Latest") |

- A variante `-trixie` (Debian, glibc) e não `-alpine` (musl): a ordenação de textos (collation) do PostgreSQL depende da biblioteca C, e a glibc é a dos ambientes de produção mais comuns. A diferença vai para a página de estudo.
- Particularidade de versão a registrar no `docs/versoes.md` e na página de estudo: a partir do PostgreSQL 18, a imagem oficial guarda os dados em `/var/lib/postgresql/18/docker`, e o volume é montado em `/var/lib/postgresql`. Até a 17, o ponto de montagem era `/var/lib/postgresql/data`.

**`compose.yaml` (raiz).**
- `name: arquitetura-debaixo-do-capo` (nome do projeto do Compose, prefixo dos containers e do volume).
- Serviço `postgres`: `image: postgres:18.6-trixie`; `profiles: [mvp]`; `environment` com `POSTGRES_DB`, `POSTGRES_USER` e `POSTGRES_PASSWORD` lidos do `.env`, todos obrigatórios (`${POSTGRES_PASSWORD:?defina POSTGRES_PASSWORD no .env (copie de .env.example)}`, e o equivalente para os outros dois); `ports: ["127.0.0.1:5432:5432"]`; volume nomeado `postgres-data` montado em `/var/lib/postgresql`; `healthcheck` com `pg_isready -U "$$POSTGRES_USER" -d "$$POSTGRES_DB"`, `interval: 5s`, `timeout: 3s`, `retries: 20`; limite de memória `1g` em `deploy.resources.limits.memory` [meta].
- Serviço `observability`: `image: grafana/otel-lgtm:0.40.0`; `profiles: [mvp]`; `ports: ["127.0.0.1:3000:3000", "127.0.0.1:4318:4318"]` (Grafana e OTLP por HTTP, Q-019); sem volume (os dados de telemetria são descartáveis no laboratório); limite de memória `2g` [meta: o README da imagem diz que 1 GB é insuficiente e usa 2 GB por padrão]; `healthcheck` que consulta `http://localhost:3000/api/health` com um programa que **exista dentro da imagem** (`curl` ou `wget`). Se a imagem não tiver nenhum dos dois, **parar e registrar uma Q**.
- Nenhum outro serviço. Nenhuma `version:` no topo (o Compose v2 ignora e avisa).

**`.env.example` (raiz).** Comentário explicando que é um modelo, que o `.env` real nunca vai para o git (`.gitignore` já cobre) e que os valores são de desenvolvimento local: `POSTGRES_DB=lab`, `POSTGRES_USER=lab`, `POSTGRES_PASSWORD=lab`.

**`scripts/compose-lint.sh [arquivo]`** (padrão: `compose.yaml` na raiz do repositório; bash, sem dependências além de grep, awk e sed):
1. Cada linha `image:` precisa de uma tag explícita (o trecho depois do último `/` tem `:`) diferente de `latest`, ou de um digest (`@sha256:`). Senão: `ERRO linha <n>: imagem sem versão fixa: <imagem>`.
2. Cada item da lista `ports:` na forma curta (`- "a:b:c"` ou `- a:b:c`) precisa começar com `127.0.0.1:`. Senão: `ERRO linha <n>: porta publicada fora de 127.0.0.1: <item>`. A forma longa (`- target: ...`) é recusada com `ERRO linha <n>: use a forma curta "127.0.0.1:<host>:<container>"`, e a forma de fluxo numa linha só (`ports: [...]`) com `ERRO linha <n>: use a lista em várias linhas ...` (Q-020), para a regra continuar simples de verificar. Um comentário no fim da linha `ports:` não desliga a verificação.
3. Saída: com erro, todas as linhas de erro e `exit 1`; sem erro, `<arquivo>: ok` e `exit 0`. Arquivo inexistente: mensagem e `exit 2`.

**`scripts/test/test-compose-lint.sh`** (estilo dos testes do harness: um arquivo temporário por cenário, `PASSOU`/`FALHOU`, `exit 1` se algum falhar). A marcação fica no **início da linha** de cada cenário, onde o teste se declara (forma que continua válida qualquer que seja a decisão sobre a regra de marcação, ainda em aberto):
1. `# covers: RNF-009` · um compose válido (tag fixa, portas em `127.0.0.1`, inclusive uma imagem com digest) → `exit 0`.
2. `# covers: RNF-001` · `image: postgres:latest` → `exit 1` com "imagem sem versão fixa".
3. `# covers: RNF-001` · `image: postgres` (sem tag) e `image: registry.example.com:5000/app` (o `:` da porta do registro não é tag) → `exit 1`, um erro para cada.
4. `# covers: RNF-009` · `- "8080:8080"` e `- "0.0.0.0:8080:8080"` → `exit 1`, um erro para cada.
5. `# covers: RNF-009` · porta na forma longa → `exit 1` com "use a forma curta".
6. `# covers: RNF-001` · o `compose.yaml` real do projeto → `exit 0`.

**CI.** No job `harness` do `.github/workflows/ci.yml`, acrescentar os passos: `bash scripts/test/test-compose-lint.sh`; `bash scripts/compose-lint.sh`; e a validação de sintaxe `cp .env.example .env && docker compose --profile mvp config --quiet`. Nenhuma action nova.

**README.** Nova seção "Como subir a infraestrutura local", antes de "Como compilar e testar o backend", com: o pré-requisito (Docker Desktop no Windows ou Docker Engine com Compose v2); o que sobe (PostgreSQL e a pilha de observabilidade, com as portas e o que cada uma faz); os comandos em blocos `bash` e `powershell` (copiar o `.env.example` para `.env` — `cp .env.example .env` / `Copy-Item .env.example .env` — e `docker compose --profile mvp up -d --wait`); como conferir (`docker compose ps`, com os dois serviços `healthy`; o Grafana em `http://localhost:3000`, usuário e senha `admin`/`admin`, que são o padrão da imagem de desenvolvimento); como parar (`docker compose --profile mvp down`) e como apagar também os dados (`docker compose --profile mvp down -v`, explicando o que o `-v` apaga).

**Segurança.** Só os valores de desenvolvimento do `.env.example` vão para o git. Todas as portas em `127.0.0.1` (D-13).

## Critérios de aceite
- **AC-RNF-001.2** Dado o `compose.yaml`, quando `scripts/compose-lint.sh` roda, então nenhuma imagem usa `latest` nem fica sem tag; uma imagem `postgres:latest` inserida de propósito faz o script sair com código 1.
- **AC-RNF-009.1** Dado o `compose.yaml`, quando `scripts/compose-lint.sh` roda, então toda porta publicada está ligada a `127.0.0.1`; uma porta `"8080:8080"` inserida de propósito faz o script sair com código 1.
- **AC-T004.1** Dado um clone limpo com o Docker instalado, quando o `.env` é criado a partir do `.env.example` e `docker compose --profile mvp up -d --wait` é executado, no Git Bash e no Windows PowerShell 5.1, então o comando termina com código 0 e `docker compose ps` mostra `postgres` e `observability` como `healthy`.
- **AC-T004.2** Dado o PostgreSQL no ar, quando `docker compose exec postgres psql -U lab -d lab -tAc "show server_version"` é executado, então a resposta começa com `18.6`; e uma tabela criada antes de `docker compose --profile mvp down` continua existindo depois de um novo `up` (o volume persiste).
- **AC-T004.3** Dada a observabilidade no ar, quando `GET http://localhost:3000/api/health` e `GET http://localhost:3000/api/datasources` (com `admin`/`admin`) são feitos, então o primeiro responde `200` e o segundo lista fontes de dados com os UIDs `tempo`, `loki` e `prometheus` (o `tempo` é o que a tela do laboratório usa no link "Ver o trace", RF-008).
- **AC-T004.4** Dada a observabilidade no ar, quando um span de teste em JSON é enviado por `POST http://localhost:4318/v1/traces`, então a resposta é `200`, e o trace aparece no Tempo pela API do Grafana.
- **AC-T004.5** Dado um clone sem `.env`, quando `docker compose --profile mvp config` é executado, então o comando falha com uma mensagem que cita `POSTGRES_PASSWORD` e o `.env.example`.
- **AC-T004.6** Dados os dois serviços no ar e ociosos, quando `docker stats --no-stream` é executado, então a memória de cada um fica abaixo do limite (1 GiB e 2 GiB), e os valores medidos, com data e ambiente A2, vão para a evidência como linha de base da RNF-007.
- **AC-T004.7** Dado um PR desta tarefa, quando o job `harness` roda, então os passos `test-compose-lint.sh`, `compose-lint.sh` e `docker compose --profile mvp config --quiet` terminam verdes.
