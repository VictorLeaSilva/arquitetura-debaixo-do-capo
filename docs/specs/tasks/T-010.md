## Objetivo
Criar o esquema do banco (as seis tabelas de `03 §3`, por migrações Flyway) e a carga determinística dos dados de referência (A1, D-09): numa única transação, o `lab` manda cada módulo limpar e carregar as próprias tabelas, pela API dele. Prova os três riscos obrigatórios de `04 §3.1` desta tarefa: carga não determinística (dois bancos), carga pela metade (`SeedFailpoint`) e execuções apagadas por uma recarga (`lab_run` preservada). Também aplica a Q-018 no harness, para que a matriz conte o RF-001 só pelos testes desta tarefa.

## Decisões da tarefa
**Dependências (versões do BOM do Spring Boot 4.1.2, conferidas em 2026-11-13: Flyway 12.4.0, driver 42.7.14, Testcontainers 2.0.5):**
| Coordenada | Escopo | Motivo |
|---|---|---|
| `org.springframework.boot:spring-boot-starter-flyway` | compile | Flyway (D-14); já traz o `spring-boot-starter-jdbc` (o `JdbcClient` e o gerenciador de transações) |
| `org.flywaydb:flyway-database-postgresql` | compile | o suporte ao PostgreSQL saiu do núcleo do Flyway desde a linha 10 |
| `org.postgresql:postgresql` | runtime | driver JDBC |
| `org.testcontainers:testcontainers-postgresql` | test | PostgreSQL real nos testes (`04 §3`) |

A carga usa SQL puro pelo `JdbcClient` (D-09: `generate_series` e fórmulas). JPA e Hibernate entram só na T-014.

**Migrações** (`backend/src/main/resources/db/migration/`), uma por módulo dono, com as colunas, tipos e constraints exatamente como em `03 §3`:
- `V1__catalog.sql`: `category`, `product` (com o índice `ix_product_category`) e `product_attribute` (com `ix_attribute_product` e o UNIQUE (`product_id`, `name`)). O CHECK do formato do `sku` é `sku ~ '^SKU-[0-9]{7}$'`.
- `V2__inventory.sql`: `flash_sale_stock`.
- `V3__ordering.sql`: `customer_order`, com `ix_order_lab_run` (`lab_run_id`, `lab_variant`) e **sem** FK para `lab_run` (D-17).
- `V4__lab.sql`: `lab_run`.
- Os nomes dos índices são os de `03 §3`; PK, FK, UNIQUE e CHECK ficam com os nomes padrão do PostgreSQL (sem `CONSTRAINT <nome>`). Nenhuma coluna usa `GENERATED ... AS IDENTITY`: os ids de `category` e `product` vêm da série, e o de `product_attribute` é `i * 10 + k` (no máximo 8 atributos por produto, então não há colisão), para que a carga seja determinística também nos ids.

**Classes** (pacote base `io.github.victorleasilva.capo`). A carga é infraestrutura, não regra de negócio: as classes de API usam o `JdbcClient` direto, sem domínio nem portas; o domínio do estoque e do pedido nasce na T-020 (P2).
| Classe | Papel |
|---|---|
| `catalog.api.CatalogSeed` (`@Component`) | `void clear()`: `DELETE FROM product_attribute`, depois `product`, depois `category`. `void load(int products)`: categorias, produtos, `seedFailpoint.afterProducts()`, atributos, com o SQL abaixo. `long countProducts()` |
| `catalog.api.SeedFailpoint` (interface) | A porta de A1, passo 5: `void afterProducts()` |
| `catalog.NoOpSeedFailpoint` (`@Component`) | A implementação de produção, que não faz nada |
| `inventory.api.InventorySeed` (`@Component`) | `void clear()`: `DELETE FROM flash_sale_stock`. `void load()`: produto 1 com `initial_quantity` = `available` = 10 |
| `ordering.api.OrderingSeed` (`@Component`) | `void clear()`: `DELETE FROM customer_order` |
| `lab.seed.SeedSettings` | `static int parse(String raw)`: o valor de `LAB_SEED_PRODUCTS`; ausente → `1000000`; senão, inteiro de 1 a 1.000.000. Inválido → `IllegalStateException` com a mensagem `LAB_SEED_PRODUCTS inválido: "<valor>" (use um inteiro de 1 a 1000000)` |
| `lab.seed.ReferenceDataSeeder` (`@Component`, `ApplicationRunner`) | Executa A1 (abaixo) na inicialização |

Por que `DELETE` e não `TRUNCATE`: o PostgreSQL recusa `TRUNCATE` numa tabela referenciada por FK de outra tabela, mesmo vazia, a menos que todas entrem no mesmo comando ou com `CASCADE`, o que faria um módulo mexer nas tabelas de outro (`01 §3`).

O `Clock` é um `@Bean` (`Clock.systemUTC()`) declarado em `CapoApplication`, o único lugar compartilhado que já existe; nenhum pacote novo de configuração é criado.

**Algoritmo do `ReferenceDataSeeder.run` (A1, sem o passo 2, que é da T-012):**
1. `int n = SeedSettings.parse(environment.getProperty("LAB_SEED_PRODUCTS"))`. A exceção sobe e a aplicação não sobe; o Spring Boot imprime a mensagem no log (AC-001.4). Nada é inserido (as tabelas existem, criadas pelo Flyway, e ficam vazias).
2. Se `catalogSeed.countProducts() == n`: registrar `seed.skipped` com `products` = n e terminar (AC-001.2).
3. `Instant start = clock.instant()`; numa única transação (`TransactionTemplate`): `orderingSeed.clear()`, `inventorySeed.clear()`, `catalogSeed.clear()`, `catalogSeed.load(n)`, `inventorySeed.load()`. `lab_run` não é tocada (D-17).
4. Depois do commit: `durationMs = Duration.between(start, clock.instant()).toMillis()`; guardar o valor no *gauge* e registrar `seed.completed` com `products` = n e `duration_ms` = durationMs.
5. Os eventos são registrados com a API fluente do SLF4J, mensagem igual ao nome do evento e os campos como pares chave-valor: `log.atInfo().setMessage("seed.completed").addKeyValue("products", n).addKeyValue("duration_ms", durationMs).log()`. O formato JSON da saída é da T-015 (D-16).
6. *Gauge*: `TimeGauge.builder("lab.seed.duration", <AtomicLong com os ms>, TimeUnit.MILLISECONDS, AtomicLong::doubleValue)` registrado no `MeterRegistry` no construtor do `ReferenceDataSeeder`; vale 0 até a primeira carga e não muda num `seed.skipped`. O Prometheus o expõe como `lab_seed_duration_seconds`.
7. Como a carga roda num `ApplicationRunner`, o Spring Boot só publica o *readiness* `ACCEPTING_TRAFFIC` depois dela; a prova do AC-008.9 é da tela (T-016) e da subida em container (T-018).

**SQL da carga** (`n` passado como parâmetro nomeado `:n`, tipo `bigint`):
```sql
INSERT INTO category (id, name)
SELECT c, 'Categoria ' || lpad(c::text, 2, '0') FROM generate_series(1, 50) AS c;

INSERT INTO product (id, sku, name, category_id, price, created_at)
SELECT i, 'SKU-' || lpad(i::text, 7, '0'), 'Produto ' || i, 1 + (i % 50),
       10.00 + ((i * 7919) % 99000)::numeric / 100, TIMESTAMPTZ '2026-01-01T00:00:00Z'
FROM generate_series(1::bigint, :n) AS i;

INSERT INTO product_attribute (id, product_id, name, value)
SELECT i * 10 + k, i, 'attr-' || k, 'valor-' || ((i * k * 31) % 1000)
FROM generate_series(1::bigint, :n) AS i
CROSS JOIN LATERAL generate_series(1::bigint, 3 + (i % 6)) AS k;
```
Conferência com o AC-001.3, produto 42: categoria `1 + 42 % 50` = 43; preço `10.00 + (332598 % 99000) / 100` = `10.00 + 355.98` = `365.98`; `3 + 42 % 6` = 3 atributos, com `(42 × k × 31) % 1000` = 302, 604 e 906.

**Testes** (todos com `@Tag("RF-001")`, exceto o do harness):

Cada teste usa o próprio banco, sem um container por teste.
- `support.SeedApplication` (só de teste): sobe a aplicação com `SpringApplicationBuilder(CapoApplication.class, <fontes extras>)`, `WebApplicationType.NONE`, e as propriedades `spring.datasource.url`, `spring.datasource.username`, `spring.datasource.password` e `LAB_SEED_PRODUCTS`; devolve o contexto, que o teste fecha. Subir de novo no mesmo banco é o "reinício" dos AC.
- `CapoApplicationTests` (já existe) passa a usar o banco de teste: `@DynamicPropertySource` com o `PostgresTestDatabase` e `LAB_SEED_PRODUCTS=10000`.
- `lab.seed.SeedSettingsTest` (unidade): válidos `"1"`, `"10000"`, `"1000000"` e ausente (→ `1000000`); inválidos `"0"`, `"-5"`, `"1000001"`, `"abc"` e `""`, cada um com a mensagem exata.
- `SchemaMigrationTest`: num banco novo, `flyway_schema_history` tem as versões 1 a 4 com `success = true`; e o banco recusa `price = 0`, `sku = 'X'`, `available = -1`, `initial_quantity = 101`, `lab_variant = 'x'` e `status = 'X'`, e aceita um `customer_order` com `lab_run_id` que não existe em `lab_run` (D-17).

## Critérios de aceite
- **AC-001.1** Dado um banco vazio e `LAB_SEED_PRODUCTS=10000`, quando a aplicação termina de inicializar, então `product` tem `10000` linhas, `category` tem `50`, cada produto tem entre 3 e 8 linhas em `product_attribute`, e `flash_sale_stock` tem 1 linha (produto 1, `available` = 10).
- **AC-001.2** Dado um banco já carregado com 10.000 produtos e o mesmo `LAB_SEED_PRODUCTS`, quando a aplicação reinicia, então nenhuma linha é inserida nem apagada e o log registra o evento `seed.skipped`.
- **AC-001.3** Dado `LAB_SEED_PRODUCTS=10000`, quando a carga termina, então o produto `SKU-0000042` tem `name` = `Produto 42`, categoria `Categoria 43`, `price` = `365.98`, `created_at` = `2026-01-01T00:00:00Z` e exatamente 3 atributos: `attr-1` = `valor-302`, `attr-2` = `valor-604` e `attr-3` = `valor-906`. O mesmo vale em dois bancos diferentes (determinismo).
- **AC-001.4** Dado `LAB_SEED_PRODUCTS` igual a `0`, `-5`, `1000001` ou `abc`, quando a aplicação inicializa, então ela não sobe, o log cita a chave `LAB_SEED_PRODUCTS` e o valor recebido, e nenhuma linha é inserida.
- **AC-001.5** Dado o ponto de falha de teste da carga configurado para falhar depois de inserir os produtos e antes dos atributos, quando a carga roda, então nada é confirmado (`product` continua com as linhas de antes); e, quando a aplicação reinicia sem o ponto de falha, a carga termina e as contagens de AC-001.1 valem.
- **AC-001.6** Dado um banco com 10.000 produtos, pedidos e 2 execuções em `lab_run`, quando a aplicação reinicia com `LAB_SEED_PRODUCTS=20000`, então `product` tem exatamente `20000` linhas geradas do zero, `customer_order` fica vazia, as 2 linhas de `lab_run` continuam intactas (todas as colunas iguais), e o log registra `seed.completed`.
- **AC-T010.1** Dado um banco novo, quando o Flyway roda, então as versões 1 a 4 estão aplicadas com sucesso, as constraints de `03 §3` recusam os seis valores inválidos listados em "Testes" e um `customer_order` com `lab_run_id` inexistente é aceito.
- **AC-T010.2** Dada uma carga concluída, quando o log e as métricas são lidos, então `seed.completed` tem os pares `products` = 10000 e `duration_ms` ≥ 0, e o *gauge* `lab.seed.duration` existe no `MeterRegistry` com valor ≥ 0 em segundos.
- **AC-T010.3** Dado um teste de script cuja única menção a um requisito está dentro de um texto, quando a matriz é gerada, então ele não conta como cobertura; e um `@Tag` no começo da linha de um teste Java conta.
